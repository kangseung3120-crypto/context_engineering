# TIL 2026-10-28 · Context Engineering

Oct 28, 2026 · @강승규

**오늘의 한 줄:** 좋은 컨텍스트는 정보를 많이 모은 결과가 아니다. 필요한 정보를, 유효한 범위에서, 예산 안에, 권한에 맞게 넣는 것이다.

무엇을 넣고 누구의 것을 언제까지 기억할지(1–2장), 길어지면 줄이고 섞이면 거르는 법(3–4장)을 배웠다. 모든 예시는 질문 하나를 끝까지 따라갔다: "13만원짜리 숙소를 예약해도 정산할 수 있나요?"

## 1-1 입력 구성

질문 하나에도 여러 종류의 입력이 필요하다. 규정 문서(한도 12만원), 도구 결과(승인 여부), 메모리(간결한 설명 선호)가 함께 들어간다.

- **PE vs RAG vs CE**: PE는 어떻게 지시할지, RAG는 어떤 문서를 찾을지, CE는 요청에 필요한 입력 전체를 어떻게 관리할지를 묻는다. CE는 대체가 아니라 확장이다.
- **kind ≠ role**: `kind`(document, tool\_result, memory)는 앱이 붙인 분류이고, `role`(system, user, assistant, tool)은 API의 역할이다.
- **출처 표지**: 자료마다 `[id / kind / source]`를 붙여 어느 근거인지 추적한다. 표지는 추적용이지 신뢰성 보증이 아니다.
- **조립**: 지시는 system, 자료와 현재 질문은 user에 넣는다. 질문은 `현재 질문:` 표지 뒤에 둔다.
- 문서 속 명령문("이전 지시를 무시하라")은 지시가 아니다. 출처와 실행 권한은 별개다.
- 컨텍스트에 넣는 것은 학습이 아니다. 다음 요청에서 쓰려면 다시 전달해야 한다.

## 1-2 우선순위

검색 점수가 높아도 권한 위반이나 만료를 상쇄할 수 없다. 점수 1.00(다른 사용자 메모)과 0.99(구버전 규정)가 가장 먼저 빠졌다.

1. **접근 범위**: 현재 사용자가 읽을 수 있나?
2. **유효성**: 현행 문서인가, 만료되지 않았나?
3. **일관성**: 같은 사실을 다르게 말하지 않나?
4. **관련성**: 앞을 통과한 자료끼리만 점수로 비교한다.
5. **예산**: 전체 입력이 한도에 들어가나?

- `exclusion_reason`은 제외 사유 또는 `None`을 돌려준다. 제외된 문서는 본문 없이 ID와 사유만 로그에 남긴다.
- 정렬 키 `(-score, id)`: 점수 내림차순, 같으면 ID 순.
- **중복과 충돌은 다르다.** 완전히 같으면 한 번만 넣고, 현행 규정끼리 값이 다르면 범위와 시행일을 비교하고 단정을 보류한다.
- **Skills**: 작업별 절차 묶음을 필요할 때만 골라 불러온다(Progressive Disclosure). 골랐다고 그 안의 명령을 실행해도 되는 것은 아니다. 키워드 방식은 "호텔비" 같은 다른 표현을 놓친다.

## 2장 메모리

단기와 장기 메모리는 저장 장소가 아니라 쓰임으로 나눈다. 지금 작업을 이어 가면 단기, 다음 세션에도 다시 쓰면 장기다.

| 후보 | 특징 | 결정 |
| --- | --- | --- |
| m1 | 선호 · 동의 · 30일 | 장기 저장 (만료 2026-11-07) |
| m2 | 지금 A호텔 비교 중 | 현재 대화만 |
| m3 | 비밀 값 | 저장하지 않음 |
| m4 | 선호 · 동의 없음 | 확인 필요 |
| m5 | 선호 · ttl 0 | 확인 필요 |

- `decide_memory`는 **결정과 이유를 함께** 돌려준다. 검사 순서는 secret → session → 동의 → 보존 기간.
- `type(ttl) is int`를 쓴다. `bool`은 `int`의 하위 타입이라 `isinstance(True, int)`가 참이 되기 때문이다.
- **만료 ≠ 삭제**: 만료는 조회에서 빼는 필터일 뿐, 저장소에서 자동으로 지워지지 않는다.

**Mem0 흐름: ID 하나를 끝까지 따라간다**

1. `add(..., infer=False)`로 저장하고, 응답에서 `event == "ADD"`인 ID만 꺼낸다.
2. `owned_record`로 현재 사용자의 기억인지 확인한다.
3. 같은 ID로 `update` 또는 `delete`한다.
4. 다시 조회해서 반영됐는지 확인한다.

검색 결과의 `[0]`을 수정하면 다른 기억을 바꿀 수 있다. 활성 목록에서 삭제돼도 `history.db`에는 이력이 남을 수 있다. 임베딩은 비슷한 기억을 찾는 도구일 뿐 저장 정책이나 권한을 대신하지 않는다.

## 3-1 토큰 예산과 Sliding Window

요청 한 번은 정해진 칸 수의 공책 한 장이다. 내 입력과 모델의 답이 이 한 장을 나눠 쓰므로, **답 칸을 먼저 떼어 둔다.**

```latex
\text{입력 예산} = \text{요청 한도} - \text{출력 예약} - \text{여유분}
```

- 글자 수, 바이트 수, 토큰 수는 다르다. "안녕하세요"는 5글자지만 Qwen3 기준 3토큰이다.
- 본문만 세지 않고 **chat template까지 적용한 전체 메시지**를 센다. role 표시와 답변 시작 표시도 토큰을 쓴다.
- `select_recent`는 (질문, 답변) 쌍을 한 턴으로 묶고, 최신 턴부터 넣다가 넘치는 순간 멈춘다. 오래된 짧은 턴을 건너뛰어 끼우지 않는다.

| 요청 한도 | 입력 예산 | 사용 | 남은 턴 |
| --- | --- | --- | --- |
| 256 | 96 | 85 | 1 (예산 이야기만) |
| 512 | 352 | 265 | 6 |
| 1024 | 864 | 265 | 6 |

**길이 통과 ≠ 근거 보존.** 한도 256에서는 칸 안에 들어갔지만 질문(담당자, 마감일)에 답할 정보가 잘려 나갔다. 출력 예약을 64로 줄이면 3턴이 들어오지만 답 칸이 줄어든다. 입력과 출력은 트레이드오프다.

128과 32는 수업용 설정값이다. 실제 서비스에서는 답변 길이(FAQ는 짧게, 코드·보고서는 길게)에 맞춰 정하고, 답이 잘리거나 입력이 잘리는지 보면서 조정한다.

## 3-2 요약과 압축

짧게 줄였다고 좋은 요약이 아니다. 질문에 필요한 조건이 다 남아 있어야 한다.

**대화 줄이기: 구조화 상태(메모장)**

- 현재 값, 이전 값, 출처를 함께 남긴다. 예: 담당자 이과장(t4), 이전 값 김대리(t1).
- 같은 필드가 다시 나오면 기존 값을 `previous`로 옮기고 `current`를 `event.copy()`로 바꾼다.
- "나중 말이 이긴다"는 **승인된 변경을 시간순으로 정리했다는 가정**에서만 맞다. 제안이나 다른 문서의 값이면 "확인 필요"로 둔다.

**문서 줄이기: 원문 추출(형광펜)**

- 문장을 고쳐 쓰지 않고 `[p1] 원문`처럼 ID와 함께 그대로 가져온다. 숫자와 조건 문구가 보존된다.
- `missing_evidence` = 필요한 ID − 남긴 ID. 한도(p1)만 남기면 p2(사전 승인), p3(미승인 미정산), p4(영수증)가 빠져 13만원 질문에 답할 수 없다.

**기타**

- 압축률 = 1 − 압축 후 토큰 / 압축 전 토큰. 높다고 품질이 좋은 것은 아니다.
- 한 번에 못 읽는 문서는 Map(구간별 요약) → Reduce(합치기). 앞 단계에서 빠진 사실은 뒤에서 복구할 수 없다.

## 4장 Prompt Caching과 Prompt Injection

**Prompt Caching: 고정은 앞, 요청별 값은 뒤**

- Prefix cache는 여러 요청이 공유하는 앞부분의 계산을 재사용한다. 줄어드는 건 Prefill(입력 처리)이고, 답변은 새로 만든다.
- 요청 ID를 system 맨 앞에 두면(A) 공통 앞부분이 11토큰, 정책을 앞에 고정하고 ID를 user로 보내면(B) 94토큰이다. 정책 버전이 바뀌면 8토큰으로 줄어드는데, 이는 정상이다.
- 공통 토큰 수는 구조 지표일 뿐 실제 캐시 사용량이 아니다. 실제 재사용은 서버 지표(`prompt_eval_cached_count` 등)로 확인한다.
- 지표를 읽을 때 `None`(알 수 없음)과 `0`(0개)을 구분한다. `if not value`로 쓰면 둘이 합쳐진다.

**오염과 Injection: 범위 먼저, 본문은 나중**

- 컨텍스트 오염의 원인은 공격만이 아니다. 접근 범위 위반, 오래된 정보, 기억·요약 오류, Prompt Injection(직접/간접)이 있다.
- 메타데이터로 조직과 현행 여부를 먼저 확인하고, 통과한 문서만 본문을 읽는다.
- 문자열 필터는 두 방향으로 틀린다. 공격 문구를 인용한 보안 가이드를 막는 **오탐**, 표현을 바꾼 공격을 통과시키는 **미탐**.
- 그래서 실행 직전에 `validate_action`으로 다시 검사한다: 사용자 권한 → 허용 도구 → 인자 키가 정확히 `{"query"}` → 빈 검색어 아님.
- 한 단계로 다 막을 수 없다. 조회, 조립, 메모리, 실행, 결과 검토 단계마다 다른 검사를 한다. 모델이 "승인 완료"라고 써도 호출 기록이 없으면 받아들이지 않는다.
